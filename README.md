## ソフトウェア開発

LLMを実装のシーケンサとして使いながら、  
**頭の中のアーキテクチャをそのままCodingするVibe感**を大切にしています。

開発するときは、前提や複数の解釈、証拠、反例、不確実な部分などをなるべく分けて考えます。

そのために、**推論・コード監査・文書整合性・外部LLM参照をそれぞれ分離した、複数の独自LLM制御系を組み合わせて**VibeCodingしています。

ひとつのLLMやひとつの評価系だけをそのまま正解にはせず、  
必要に応じて別の系から見直すようにしています。

現在取り組んでいる研究開発の多くは非公開ですが、  
公開できるものは少しずつ切り出して公開しています。

## 公開研究・ソフトウェア

### Epistesys

AIに長く複雑な仕事を任せるための、  
**外部推論制御 / AI reliability research project**です。

VibeCodingでは、LLMがそれっぽい答えやコードを出すことよりも、

- 何をどう解釈したのか
- どの情報を根拠にしたのか
- まだ何が分かっていないのか
- どの制約を守る必要があるのか
- どこまで検証できたのか
- その結果を本当に確定・出力してよいのか

を途中で見失わないことを重視しています。

Epistesysは、  
**解釈・状態・証拠・権限・計算・検証・出力commitを、LLMの外側からひとつの制御経路として扱う**  
ための実験的なアーキテクチャです。

長い指示や複雑な依存関係でも、

- 「分からないこと」を「分かったこと」にしない
- 候補をそのまま確定しない
- 制約や未解決事項を保持する
- 過去の判断や証拠まで追跡できる
- 確定前に再検証できる

VibeCoding / Agent開発を目指しています。

現在の公開alphaはbaseline implementationです。  
hallucination低減や長期タスクでの信頼性向上そのものは、  
今後benchmark・独立評価していく研究仮説です。

[Epistesys](https://github.com/ViszCham/Epistesys)

### RepoSeiri

AIがリポジトリを  
**ファイルの集合ではなく、命題・能力・証拠の構造として読む**  
ためのRust製semantic auditorです。

READMEに書かれていることと、  
実際にrepositoryから確認できるevidenceを命題単位で照合して、

- 実装されているのにREADMEへ出ていない能力
- 根拠より強く言いすぎているclaim
- まだ判断できないこと
- 変更によって意味がズレた箇所

を分けて扱います。

VibeCodingでAIに大きな変更を任せても、  
「コードがある」「テストが通る」だけで  
READMEや成果まで勝手に強く主張しないための、  
**repository-levelの意味・claim governance layer**として使っています。

「分からない」を勝手に「存在しない」にしないことや、  
解析することと実際に変更する権限を分けることなど、  
普段の開発で大切にしている考え方を形にしたものです。

[RepoSeiri](https://github.com/ViszCham/RepoSeiri)
